Roadmap delle versioni

Le versioni seguono il numero semantico: la terza cifra corregge errori, la seconda aggiunge funzioni compatibili, la prima cambia qualcosa che richiede un intervento sul database o sulle configurazioni. Un aggiornamento di minor o patch si applica dal pannello; un passaggio di major va pianificato con assistenza.

  1. v1.1.13 12 ottobre 2026 Disponibile

    Aggiornamenti, branding e guide offline

    È la versione che stai documentando: controllo versione da GitHub con backup e rollback, loghi nel pannello, guide consultabili senza connessione. Versione attuale

  2. v1.2.0 primo trimestre 2027 In sviluppo

    Sistema di moduli aggiuntivi

    Nuova cartella modules/, manifest module.json, pagina Moduli dentro Sistema & Sincro e attivazione con controllo di compatibilità. Gli aggiornamenti del core smettono di sovrascrivere le personalizzazioni: le funzioni extra vivono fuori dai file dell'applicazione.

  3. v1.3.0 2027 Pianificata

    Notifiche al paziente

    Avviso quando mancano un numero configurabile di turni, con template per servizio e registro degli invii. Il canale (SMS, WhatsApp o notifica web) dipende dal fornitore scelto dalla struttura: senza un gateway configurato il modulo resta spento.

  4. v1.4.0 2027 Pianificata

    Turno da remoto e appuntamenti

    Presa del numero da smartphone tramite QR all'ingresso e agenda per servizio, con il turno prenotato che entra in coda all'orario previsto. Richiede un fuso orario coerente tra server e postazioni.

  5. v2.0.0 da definire In valutazione

    Multi-sede e integrazioni

    Più strutture su una sola installazione, monitor aggregato e API per CUP e anagrafica pazienti. È un passaggio major perché tocca lo schema del database: va pianificato con una migrazione assistita, non con il pulsante di aggiornamento.

Come funzionerà il sistema di moduli

Un modulo è una cartella autonoma che aggiunge funzioni senza modificare le pagine del core. L'obiettivo è uno solo: permettere personalizzazioni che sopravvivono agli aggiornamenti, invece di essere cancellate alla prima sovrascrittura.

modules/
└── notifiche/
    ├── module.json          manifest: nome, versione, compatibilità
    ├── notifiche.php        logica del modulo
    ├── config.php           impostazioni specifiche (escluso dagli update)
    ├── assets/              stili e immagini del modulo
    └── logs/                registro del modulo
Campo di module.jsonUso
chiaveIdentificativo univoco, usato per cartella, tabelle e permessi
nome, descrizioneTesti mostrati nella pagina Moduli
versioneVersione del modulo, indipendente da quella del core
compatibilitaIntervallo di versioni del core, per esempio >=1.2.0 <2.0.0
pannelloSezioni aggiunte al menu e relativi permessi
configFile di configurazione da non sovrascrivere negli aggiornamenti
 
{
  "chiave": "notifiche",
  "nome": "Notifiche al paziente",
  "versione": "1.0.0",
  "compatibilita": ">=1.2.0 <2.0.0",
  "pannello": ["notifiche"],
  "config": "config.php"
}

Il core carica solo i moduli elencati in modules_config.json: un modulo copiato nella cartella ma non attivato non viene eseguito. L'attivazione esegue il controllo di compatibilità, registra i permessi e applica le eventuali migrazioni delle tabelle; la disattivazione spegne il modulo ma conserva file e dati.

Oggi il sistema di moduli non esiste ancora

Fino alla 1.2.0 le personalizzazioni si gestiscono come descritto in Versioning e aggiornamenti: file locali aggiunti a .updateignore. Modificare direttamente una pagina del core significa perderla al primo aggiornamento: se serve una funzione nuova, va concordata, non applicata a mano sul server.

Moduli e aggiornamenti del core

La regola è che un aggiornamento non deve mai lasciare il sistema in uno stato ambiguo. Prima di applicare l'aggiornamento il core confronta la versione nuova con il campo compatibilita di ogni modulo attivo e decide cosa fare.

SituazioneComportamento previsto
Modulo compatibileResta attivo, configurazione e dati non vengono toccati
Modulo non compatibileViene disattivato, non cancellato: file e dati restano, la pagina Moduli segnala il blocco
Cartella modules/Esclusa dagli aggiornamenti, come le configurazioni locali
modules_config.jsonEscluso: l'elenco dei moduli attivi è della singola struttura
Migrazione delle tabelleEseguita all'attivazione della nuova versione del modulo, con backup preventivo
Rollback del coreI moduli restano sul disco; vanno riallineati alla versione precedente dopo il ripristino
Prima di attivare un modulo

Verifica la compatibilità con la versione installata, prova l'attivazione su una copia del server, salva un backup dal pannello e programma l'intervento fuori dall'orario di apertura. Un modulo nuovo cambia il menu e i permessi: controlla che gli operatori vedano solo le sezioni che servono.

Regole per un modulo compatibile

  1. Non toccare il core

    Nessun modulo modifica file dell'applicazione: usa gli eventi esposti dal core (turno creato, chiamato, chiuso, giornata azzerata) e le funzioni pubbliche.

  2. Dichiara la compatibilità

    Il campo compatibilita deve indicare l'intervallo reale di versioni provate, non “tutte”. Meglio un modulo che si blocca in modo pulito che uno che rompe il pannello.

  3. Isola tabelle e configurazione

    Prefissa le tabelle con la chiave del modulo (notifiche_invii) e tieni le impostazioni in un file del modulo, escluso dagli aggiornamenti.

  4. Scrivi nel log del modulo

    Errori e azioni finiscono in modules/<chiave>/logs/: la diagnostica del core resta leggibile e si capisce subito se il problema è del modulo.

  5. Prevedi la disattivazione

    Spegnere il modulo deve riportare menu, permessi e code allo stato precedente senza perdere i dati già raccolti.

  6. Prova il rollback

    Installa, aggiorna il core, disattiva e ripristina su una copia. Se una di queste quattro operazioni lascia residui, il modulo non è pronto.

Segnalare una funzione mancante

La roadmap si costruisce dalle richieste delle strutture. Indica il caso d'uso concreto (servizio, sportello, momento della giornata) e cosa fai oggi per aggirarlo: è l'informazione che permette di capire se basta una configurazione o serve un modulo.
